Developer Fundamentals

Fundamentos del Desarrollador Salesforce

La plataforma multitenant, Apex desde cero, SOQL/SOSL y seguridad en código.

1. La Plataforma Salesforce: Multitenant y Metadata-Driven

🏗️ Arquitectura Multitenant

Múltiples organizaciones (tenants) comparten la misma infraestructura física, pero están completamente aisladas entre sí.

  • ¿Por qué importa? Esta arquitectura es la razón de ser de los Governor Limits: el sistema protege a todos los tenants de que uno solo consuma todos los recursos.
  • El código Apex se ejecuta en un runtime compartido, de ahí los límites de CPU, memoria y SOQL.

📐 Metadata-Driven Development

En Salesforce, todo (objetos, campos, flows, código) es metadata. Se almacena separado de los datos reales.

  • Esto permite mover configuración entre orgs sin mover datos.
  • El Schema Builder y el Object Manager editan metadata visualmente.
  • La Salesforce CLI (SFDX) trabaja directamente con metadata en formato XML.

2. Tipos de Datos en Apex

📌 Primitivos

  • String: Texto entre comillas simples. 'Hola Mundo'
  • Integer: Números enteros de 32 bits. 42
  • Long: Enteros de 64 bits (para números muy grandes).
  • Decimal: Números con decimales. Ideal para moneda. 9.99
  • Double: Punto flotante de 64 bits.
  • Boolean: true o false
  • ID: Identificador único de 15 o 18 caracteres. Salesforce lo convierte automáticamente.
  • Date: Solo fecha. Date.today()
  • DateTime: Fecha + hora. DateTime.now()
  • Blob: Datos binarios (para archivos y adjuntos).

📦 sObject — El Tipo Especial de Salesforce

Un sObject representa un registro de Salesforce. Puede ser genérico o específico.

// Específico (recomendado - type safe)
Account acc = new Account();
acc.Name = 'Acme';
acc.Phone = '123456789';

// Genérico (útil en métodos que trabajan con cualquier objeto)
sObject obj = new Account();
obj.put('Name', 'Acme');
  • Puedes construir un sObject pasando campos en el constructor.
  • Los campos personalizados se acceden igual: acc.Campo_Custom__c

3. Colecciones — La Base de la Bulkificación

Las colecciones son esenciales para procesar múltiples registros de una vez y respetar los Governor Limits.

TipoOrdenadaDuplicadosAccesoCaso de uso principal
List<T>✅ Sí✅ SíPor índice (0, 1, 2...)Resultados de SOQL, procesamiento secuencial.
Set<T>❌ No❌ Nocontains()Recopilar IDs únicos para filtrar en SOQL.
Map<K,V>❌ NoKeys únicasPor Key (get(key))Agrupar registros por ID. Acceso O(1).

❌ MAL — SOQL dentro de un Loop

for (Account a : accounts) {
    // SOQL en cada iteración = Governor Limit!
    List<Contact> cons = [SELECT Id FROM Contact
                          WHERE AccountId = :a.Id];
}

✅ BIEN — Bulkificado con Map

Set<Id> accIds = new Map<Id, Account>(accounts).keySet();
Map<Id, List<Contact>> contactsByAcc = new Map<Id, List<Contact>>();
for (Contact c : [SELECT Id, AccountId FROM Contact WHERE AccountId IN :accIds]) {
    if (!contactsByAcc.containsKey(c.AccountId))
        contactsByAcc.put(c.AccountId, new List<Contact>());
    contactsByAcc.get(c.AccountId).add(c);
}
💡 Tip de Examen: "Nunca pongas SOQL ni DML dentro de un loop" es la regla número 1 de Apex. Casi todas las preguntas sobre Governor Limits tienen este patrón como respuesta incorrecta que debes identificar.

4. SOQL — Salesforce Object Query Language

Para leer registros de la base de datos. Se escribe entre corchetes [...] en Apex (inline SOQL).

🔗 Relaciones en SOQL

  • Hijo → Padre (Traversal): Navegar hacia el padre usando el nombre del campo de relación.
    SELECT Account.Name FROM Contact
  • Padre → Hijos (Subquery): Usar el nombre de la relación hijo en plural.
    SELECT Id, (SELECT LastName FROM Contacts) FROM Account
  • El resultado de la subquery es una List<sObject> accesible desde el padre.

🛠️ Cláusulas y Funciones

  • WHERE field = :apexVar — Bind variable (pasar variables de Apex a SOQL).
  • ORDER BY, LIMIT, OFFSET — Paginación.
  • GROUP BY — Requiere funciones de agregado (COUNT(), SUM(), AVG()).
  • HAVING — Filtrar resultados agregados (como un WHERE para GROUP BY).
  • FOR UPDATE — Bloquea registros mientras se procesan.
// Aggregate SOQL con GROUP BY
List<AggregateResult> results = [
    SELECT StageName, COUNT(Id) total, SUM(Amount) revenue
    FROM Opportunity
    WHERE CloseDate = THIS_YEAR
    GROUP BY StageName
    HAVING COUNT(Id) > 5
];
for (AggregateResult ar : results) {
    System.debug('Stage: ' + ar.get('StageName') + ' | Count: ' + ar.get('total'));
}
🚨 Límites SOQL a recordar:
  • Máximo 100 consultas SOQL síncronas por transacción.
  • Máximo 200 consultas en modo asíncrono.
  • Máximo 50,000 registros recuperados por transacción.

5. SOSL — Salesforce Object Search Language

🔍 ¿Qué es SOSL?

Búsqueda de texto en múltiples objetos a la vez usando el motor de búsqueda (Lucene). Devuelve List<List<sObject>>.

List<List<sObject>> results = [FIND 'Acme*'
    IN ALL FIELDS
    RETURNING Account(Name, Phone), Contact(FirstName, LastName)];

List<Account> accs = (List<Account>) results[0];
List<Contact> cons = (List<Contact>) results[1];

6. Seguridad en Código: CRUD, FLS y Sharing

⚠️ El problema: Apex se ejecuta en System Mode por defecto

Por defecto, el código Apex ignora los permisos del usuario (perfiles, FLS, sharing rules). Puede leer y escribir cualquier dato. Como desarrollador, debes verificar permisos manualmente si necesitas respetar la seguridad.

🔐 With Sharing / Without Sharing

  • with sharing: La clase respeta las Sharing Rules del usuario. Los registros que no tiene acceso no aparecen en las queries.
  • without sharing: La clase ignora las reglas de sharing. Ve todos los registros.
  • inherited sharing: Hereda el contexto de quien la llamó.
public with sharing class AccountController {
    public List<Account> getMyAccounts() {
        // Solo devuelve cuentas que el usuario puede ver
        return [SELECT Id, Name FROM Account];
    }
}

🛡️ Verificar CRUD y FLS

El sharing solo controla qué registros se ven. Para controlar qué campos y objetos puede modificar el usuario, debes verificar explícitamente:

// Verificar permiso de Create en Account
if (!Schema.sObjectType.Account.isCreateable()) {
    throw new AuraHandledException('No tienes permiso de crear cuentas.');
}

// Verificar que un campo es editable
if (!Schema.sObjectType.Account.fields.Phone.isUpdateable()) {
    // No actualizar ese campo
}
💡 Tip de Examen: with sharing controla la VISIBILIDAD de registros (Sharing/OWD). Los permisos de CRUD y FLS debes verificarlos tú con Schema.sObjectType. Son conceptos distintos y el examen suele confundirlos intencionalmente.
