Testing, Debug & Deployment

Pruebas, Debugging y Despliegue

Garantizar la calidad del código y moverlo con seguridad entre entornos.

1. Apex Unit Testing — La Cobertura del 75%

Regla clave: No puedes desplegar código Apex a producción si la cobertura total de tests es inferior al 75%. Cada clase individual no necesita ser 75%, pero el agregado de toda la org sí.

📋 Reglas de los Tests en Apex

  • La clase debe anotarse con @isTest.
  • Los métodos de test deben ser static void y anotarse con @isTest (o testMethod).
  • Aislamiento: Por defecto @isTest(SeeAllData=false). Los tests NO ven datos reales de la org. Debes crear tus propios datos de test.
  • La cobertura mide líneas ejecutadas, no la corrección de la lógica.
  • Los tests no consumen governor limits de producción.

🏗️ Estructura de una Clase de Test

@isTest
private class AccountServiceTest {

    // Setup: datos que comparten todos los tests de esta clase
    @TestSetup
    static void crearDatos() {
        Account a = new Account(Name = 'Test Account');
        insert a;
    }

    @isTest
    static void testCrearCuenta() {
        // Arrange — preparar datos
        Account acc = [SELECT Id FROM Account WHERE Name = 'Test Account' LIMIT 1];

        // Act — ejecutar la lógica
        Test.startTest();
        AccountService.procesarCuenta(acc.Id);
        Test.stopTest();

        // Assert — verificar el resultado
        Account resultado = [SELECT Rating FROM Account WHERE Id = :acc.Id];
        System.assertEquals('Hot', resultado.Rating, 'El Rating debería ser Hot');
    }
}

⏱️ Test.startTest() y Test.stopTest()

  • startTest(): Resetea los governor limits dentro del bloque. El código entre start y stop tiene sus propios límites frescos.
  • stopTest(): Finaliza la ejecución y también obliga a los jobs asíncronos a completarse antes de continuar. Esencial para testar Batch Apex, @future y Queueable.
  • Solo puede haber un par startTest/stopTest por método de test.

🔌 Testar Callouts HTTP — Test.setMock()

No puedes hacer callouts reales en tests. Debes usar un Mock.

// 1. Crear la clase Mock que implementa HttpCalloutMock
@isTest
global class MockCallout implements HttpCalloutMock {
    global HttpResponse respond(HttpRequest req) {
        HttpResponse res = new HttpResponse();
        res.setStatusCode(200);
        res.setBody('{"name":"Acme"}');
        return res;
    }
}

// 2. Usarlo en el test
@isTest
static void testCallout() {
    Test.setMock(HttpCalloutMock.class, new MockCallout());
    Test.startTest();
    MiClaseDeCallout.hacerPeticion();
    Test.stopTest();
    // asserts aquí
}
💡 Tip de Examen: El propósito del test NO es solo alcanzar el 75% de cobertura — es el Assert. Un test sin System.assertEquals() no verifica nada. El examen distingue entre "código con cobertura" y "código bien testeado".

2. Debugging — Herramientas para Encontrar el Error

📋 Debug Logs

  • Dónde: Setup → Logs → Debug Logs.
  • Puedes activar logs para un usuario específico durante un tiempo determinado.
  • Los logs muestran: SOQL ejecutados, DML, excepciones, salidas de System.debug().
  • Niveles: NONE, ERROR, WARN, INFO, DEBUG, FINE, FINER, FINEST. Cada nivel añade más detalle.
  • El Developer Console los muestra en tiempo real.

🔍 Developer Console

  • Herramienta integrada en el navegador para desarrollar y depurar.
  • Execute Anonymous: Ejecuta código Apex directamente sin crear una clase. Ideal para pruebas rápidas.
  • Query Editor: Ejecuta SOQL y SOSL de forma interactiva.
  • Checkpoints: Equivalente a breakpoints; pausan la ejecución y muestran el estado del heap.
  • Log Inspector: Visualiza los debug logs con filtros por tipo.

4. Herramientas de Despliegue

📦 Change Sets

  • Herramienta declarativa dentro de Setup. No requiere herramientas externas.
  • Mueve metadatos entre orgs que están conectadas (Deployment Connections).
  • Outbound Change Set: Lo creas en el origen (sandbox) y añades los componentes.
  • Inbound Change Set: Lo validas y despliegas en el destino (producción).
  • Limitaciones: No soporta todos los tipos de metadatos. No es compatible con Git.

⚡ Salesforce CLI (SFDX)

  • Herramienta de línea de comandos para desarrolladores.
  • Trabaja con proyectos en source format (metadata como archivos locales en Git).
  • sf project deploy start — Despliega a una org.
  • sf project retrieve start — Descarga metadata de una org.
  • Permite CI/CD: despliegues automáticos desde GitHub Actions, Jenkins, etc.
  • Soporta scratch orgs para desarrollo aislado.

🔑 Requisito de Despliegue a Producción:
Al desplegar código Apex a producción, la cobertura total de tests de la org debe ser ≥75% y todos los tests deben pasar. Si despliegas un trigger, ese trigger específico también debe tener al menos alguna cobertura.
