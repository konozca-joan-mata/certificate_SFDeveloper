Clases Apex, Triggers y Automatización

El bloque más pesado del examen. Programar en Apex de forma segura y escalable.

1. Clases Apex — Estructura y Modificadores

🔒 Modificadores de Acceso

  • public: Accesible desde cualquier clase en la org.
  • private: Solo dentro de la misma clase.
  • protected: Clase y sus subclases.
  • global: Accesible desde paquetes externos y APIs.
  • virtual: Permite sobreescribir el método en una subclase.
  • abstract: La clase no puede instanciarse; debe ser extendida.
  • override: Sobreescribe un método virtual del padre.

🧬 Interfaces

Define un contrato sin implementación. Las clases que la usan implementan todos sus métodos.

public interface Notificable {
    void enviarAlerta(String msg);
}
public class EmailService implements Notificable {
    public void enviarAlerta(String msg) {
        // implementación concreta
    }
}

Las interfaces de Salesforce más comunes: Database.Batchable, Queueable, Schedulable.

❌ MAL — Lógica directamente en el Trigger

trigger AccountTrigger on Account (before insert) {
    for (Account a : Trigger.new) {
        // 200 líneas de lógica aquí...
    }
}

✅ BIEN — Patrón Handler (un trigger, una clase)

trigger AccountTrigger on Account (before insert, after insert) {
    AccountTriggerHandler h = new AccountTriggerHandler();
    if (Trigger.isBefore && Trigger.isInsert)
        h.beforeInsert(Trigger.new);
    if (Trigger.isAfter && Trigger.isInsert)
        h.afterInsert(Trigger.new);
}
💡 Tip de Examen: En before triggers puedes modificar Trigger.new sin DML adicional. En after, los registros ya tienen ID pero son de solo lectura.

3. Order of Execution

El tema más preguntado del examen PDI. Orden exacto cuando se guarda un registro:
  1. Carga el registro original de la DB (o inicializa si es nuevo).
  2. Carga los nuevos valores del request.
  3. Ejecuta System Validation Rules (tipo de dato, campos required del sistema).
  4. Ejecuta los Before Triggers.
  5. Ejecuta las Custom Validation Rules (las del Setup del Admin).
  6. Guarda el registro en la DB (sin commit todavía).
  7. Ejecuta los After Triggers.
  8. Ejecuta Assignment Rules.
  9. Ejecuta Auto-response Rules.
  10. Ejecuta Workflow Rules (Legacy). Si actualiza un campo → re-ejecuta Before Triggers y Validation Rules.
  11. Ejecuta Record-Triggered Flows (Before-save → After-save).
  12. Ejecuta Escalation Rules (solo Cases).
  13. Hace el Commit final en la DB.
  14. Ejecuta acciones post-commit (emails de Workflow, encola Async Apex).
💡 Tip de Examen: Los Before Triggers van ANTES de las Validation Rules custom. Un Workflow que actualiza un campo provoca que los Before Triggers y Validation Rules se ejecuten de nuevo — esta es la pregunta trampa más clásica.

4. Governor Limits

🚨 Límites síncronos críticos por transacción:
  • Consultas SOQL: 100 (async: 200)
  • Registros devueltos por SOQL: 50,000
  • Sentencias DML: 150
  • Registros por DML: 10,000
  • Llamadas @future: 50
  • Tiempo de CPU: 10,000 ms
  • Heap Size (memoria): 6 MB
  • Callouts HTTP: 100

🔑 Reglas para evitar los límites

  • Nunca SOQL dentro de un loop. Extrae IDs antes y usa WHERE Id IN :setDeIds.
  • Nunca DML dentro de un loop. Acumula en una List y haz un solo insert lista.
  • Usa Map<Id, sObject> para acceder a registros sin queries adicionales.
  • Para millones de registros, usa Batch Apex.

Batch Apex — Estructura obligatoria

global class BorrarLeadsViejos implements Database.Batchable<sObject> {
    // 1. start: define qué registros procesar
    global Database.QueryLocator start(Database.BatchableContext bc) {
        return Database.getQueryLocator('SELECT Id FROM Lead WHERE CreatedDate < LAST_N_YEARS:2');
    }
    // 2. execute: lógica sobre cada chunk (default 200 registros)
    global void execute(Database.BatchableContext bc, List<Lead> scope) {
        delete scope;
    }
    // 3. finish: notificación o limpieza
    global void finish(Database.BatchableContext bc) {
        Messaging.sendEmail(...);
    }
}
💡 Tip de Examen: Los métodos @future no pueden recibir sObjects como parámetros (solo primitivos como String, Integer, Set<Id>). Usa Queueable si necesitas pasar objetos complejos.

6. Manejo de Excepciones y DML Parcial

Try-Catch

try {
    insert nuevasCuentas;
} catch (DmlException e) {
    System.debug(e.getDmlMessage(0));
} catch (Exception e) {
    System.debug(e.getMessage());
} finally {
    // siempre se ejecuta
}

Database.insert con allOrNone=false

Por defecto, si un registro falla → rollback total. Con allOrNone=false permites fallos parciales:

List<Database.SaveResult> results =
    Database.insert(listaRegistros, false);

for (Database.SaveResult sr : results) {
    if (!sr.isSuccess()) {
        System.debug(sr.getErrors()[0].getMessage());
    }
}
